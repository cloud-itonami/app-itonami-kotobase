# Signed basis, policy and Forest receipt after guest reboot, 2026-11-14

The hosted composition from `SIGNED-POLICY-MULTI-RECEIPT-20261114.md` was copied to a dedicated Lima VZ Linux aarch64 guest, including only the actual source/receipt stores, fixture public-key/IDs sidecar, required source overlays and JVM jars. Writer/staging copies were not transferred. The copied bundle was approximately 11 MiB; archive SHA-256 `ef8a017c3e9781dca8a8955565a1c2e8ece39b28e08268ae2c78eb5af231a2fd`. Hashes of the guest inputs matched the included manifest before and after the experiments. macOS archive AppleDouble/xattr entries caused Linux tar warnings and extra sidecar files; the regular source/data files were checked by SHA-256.

A first `sync` and Lima stop/start changed boot ID `85a84328-7a22-4117-a14a-75523e922f25` to `abadcd68-0a67-43c3-9c8c-9a3d067e50f1`. The signed basis, recovered policy and allow/deny Forest receipts verified with no writer executable; missing request and altered basis location, policy or signature were refused. That first post-reboot run followed a full hash scan and is therefore warm in the guest. A separate task-owned copy had the first byte of one real receipt Forest file modified; a fresh reader rejected it with `Forest digest mismatch`. The original input manifest still matched. The first corruption attempt accidentally selected an AppleDouble `._` file whose first byte was already zero; its unchanged hash was detected and that attempt was not counted.

For a cold-guest-order check, a second `sync` and Lima stop/start changed boot ID `abadcd68-0a67-43c3-9c8c-9a3d067e50f1` to `5c1f25aa-2f11-4d1a-8e49-98742c305601`. The first task read after boot was the signed-basis/receipt verifier, with no prior full data hash scan and no writer. It passed the same positive and refusal checks. A subsequent process queried the recovered Prolly snapshot: valid Dango capability returned 3 rows and no capability returned 0. This query ran after the receipt verifier and is not itself a cold first read. Finally the input manifest matched again.

Guest and task-owned `.agent-output/signed-policy-guest-evidence-01` retain boot IDs, outputs and negative-control hashes.

The second restart discards guest OS page cache, but the host and storage caches were not controlled. This is a synced, explicit Lima stop/start, not a physical power cut or abrupt write interruption. The workload is the 3-row hosted JVM fixture, not Native, a GiB data read, a product service, independent nodes, trusted issuer provenance or rollback protection. Source and receipt stores remain separate and the public-key/ID sidecar is not a trust anchor. No downloads and no existing evidence were deleted.

Reproduction requires the dedicated guest and task-owned bundle retained under `~/awai-native-forest/signed-policy-guest-reboot-01` in the guest. With the guest otherwise idle, record the current boot ID, `sync`, stop/start with `limactl`, and run `sh run.sh` in that directory **before** scanning data hashes; then run `sh run-query.sh` and `sha256sum -c manifest.sha256`. Do not run this procedure on a shared or production VM.
