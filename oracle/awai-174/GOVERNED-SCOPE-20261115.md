# Request-derived hosted nonce scope — 2026-11-15

`kotobase.governed-atomic/request-scope` first structurally validates the existing RequestEnvelope and computes the canonical value CID of `{:format :kotobase.nonce/request-scope-v1, :tenant ..., :principal ..., :graph ..., :epoch ...}`. The hosted wrapper requires the host-supplied ledger scope to match that CID before calling the governed path. The host must still authenticate the request's principal, tenant, graph and epoch, choose and protect the correct durable store, verify marker semantics, and atomically publish the marker with the receipt. A structural CID is not an identity or authorization proof.

This format matches the prior GiB fixture's explicit scope. Local one-off JVM controls verified identical input gives the same CID; changes to tenant, principal, graph or epoch change it and cause the wrapper to reject the old host scope. A different nonce stays within the same scope; malformed requests and previously configured nonce consumers are refused. `governed_scope_existing_ledger.clj` reopened the preexisting fixture ledger with the new derivation, refused both previously consumed nonces with the writer unavailable, and confirmed the root was unchanged. The ledger path is supplied as `EXISTING_LEDGER`; it is not bundled with the script.

Changing graph or epoch deliberately changes the replay domain. It is not a global nonce registry: epoch freshness and cross-domain policy are the host's responsibility. Existing ledgers using another scope must not be silently adopted or replaced; migration must preserve replay protection or fail closed. The available test establishes compatibility only with the explicitly recorded prior fixture. It does not prove Native support, non-reserving preflight as an exclusive lock, production identity, independent nodes or host-cache-loss recovery.
